## ADDED Requirements

### Requirement: Environment-provided connection settings
The system SHALL read all Aurora DSQL connection settings from the runtime environment and SHALL NOT hard-code any cluster identifier, endpoint, user, or credential.

The recognized variables are:

| Variable | Required | Default |
| --- | --- | --- |
| `DSQL_CLUSTER_ENDPOINT` | yes | — |
| `DSQL_CLUSTER_USER` | yes | — |
| `DSQL_DATABASE` | no | `postgres` |
| `DSQL_PORT` | no | `5432` |
| `DSQL_SSLROOTCERT` | no | the image's system CA bundle |
| `AWS_REGION` or `AWS_DEFAULT_REGION` | no | region parsed from the cluster endpoint |

#### Scenario: All required variables are set
- **WHEN** `DSQL_CLUSTER_ENDPOINT` and `DSQL_CLUSTER_USER` are present in the environment
- **THEN** the connectivity check uses those values as the connection host and database user
- **AND** uses `postgres` as the database name and `5432` as the port when `DSQL_DATABASE` and `DSQL_PORT` are unset

#### Scenario: Optional variables override the defaults
- **WHEN** `DSQL_DATABASE`, `DSQL_PORT`, or `DSQL_SSLROOTCERT` is set in the environment
- **THEN** the connectivity check uses the supplied value in place of the corresponding default

#### Scenario: Region is resolved
- **WHEN** a connectivity check runs
- **THEN** the region is taken from `AWS_REGION` if set, otherwise from `AWS_DEFAULT_REGION` if set, otherwise parsed from the `<cluster-id>.dsql.<region>.on.aws` endpoint
- **AND** the check reports failure with the error identifier `not_configured` when no region can be resolved by any of those means

### Requirement: IAM authentication token generation
The system SHALL authenticate to Aurora DSQL using a short-lived IAM authentication token supplied as the connection password, and SHALL generate a new token for each connectivity check rather than reusing a previously generated token.

The system SHALL call `generate_db_connect_admin_auth_token` when the configured user is `admin`, and `generate_db_connect_auth_token` for any other user.

#### Scenario: Token generated for a non-admin user
- **WHEN** a connectivity check runs and `DSQL_CLUSTER_USER` is not `admin`
- **THEN** the system generates the token with `generate_db_connect_auth_token` for the configured endpoint and region
- **AND** passes that token as the connection password

#### Scenario: Token generated for the admin user
- **WHEN** a connectivity check runs and `DSQL_CLUSTER_USER` is `admin`
- **THEN** the system generates the token with `generate_db_connect_admin_auth_token` for the configured endpoint and region

#### Scenario: Two checks in succession
- **WHEN** two connectivity checks run one after the other
- **THEN** each generates its own authentication token
- **AND** neither reuses a token generated by an earlier check

#### Scenario: Token generation fails
- **WHEN** token generation raises an error, for example because no AWS credentials are available
- **THEN** the check reports failure with the error identifier `auth_token_failed`
- **AND** no connection attempt is made

### Requirement: TLS-verified connection
The system SHALL connect to Aurora DSQL with TLS certificate verification enabled, using `sslmode=verify-full`. The system SHALL verify against the certificate bundle named by `DSQL_SSLROOTCERT` when that variable is set, and against the container image's system CA bundle otherwise.

#### Scenario: Connecting without an explicit root certificate
- **WHEN** a connectivity check runs and `DSQL_SSLROOTCERT` is not set
- **THEN** the connection is made with `sslmode=verify-full` against the system CA bundle

#### Scenario: Connecting with an explicit root certificate
- **WHEN** a connectivity check runs and `DSQL_SSLROOTCERT` names a certificate bundle
- **THEN** the connection is made with `sslmode=verify-full` and that bundle as the root certificate

### Requirement: SELECT 1 probe
The connectivity check SHALL execute the query `SELECT 1` against the configured cluster and SHALL treat the check as successful only when the query returns the value `1`.

#### Scenario: Query succeeds
- **WHEN** the connection is established and `SELECT 1` returns `1`
- **THEN** the check reports success with the returned value

#### Scenario: Query fails after a successful connection
- **WHEN** the connection is established but the query raises an error
- **THEN** the check reports failure with the error identifier `query_failed`

### Requirement: Bounded connection attempt
The connectivity check SHALL apply an explicit connection timeout so that an unreachable endpoint fails within a bounded time rather than blocking until the operating system abandons the attempt.

#### Scenario: Endpoint is unreachable
- **WHEN** the configured endpoint cannot be reached, for example because network rules block TCP traffic to the cluster port
- **THEN** the connection attempt is abandoned once the configured timeout elapses
- **AND** the check reports failure with the error identifier `connection_failed`

### Requirement: Connection released after each check
The system SHALL close the database connection at the end of each connectivity check, including when the connection attempt or the query fails.

#### Scenario: Check completes successfully
- **WHEN** a connectivity check finishes and the query succeeded
- **THEN** the connection opened for that check is closed

#### Scenario: Check fails after connecting
- **WHEN** a connectivity check finishes and the query raised an error
- **THEN** the connection opened for that check is closed

### Requirement: DSQL result reported through the API endpoint
The `/api/` endpoint SHALL include a `dsql` object in its JSON response alongside the existing `cdk_bootstrap_version` field. The object SHALL contain a boolean `ok` field, a `result` field carrying the query's returned value when `ok` is true, and an `error` field carrying a failure identifier when `ok` is false.

The `cdk_bootstrap_version` field SHALL keep its existing name, value, and fallback behavior.

#### Scenario: Both dependencies reachable
- **WHEN** a client sends an HTTP GET request to `/api/` and both the SSM lookup and the DSQL probe succeed
- **THEN** the response status is 200
- **AND** the JSON body includes `cdk_bootstrap_version` with the parameter's value
- **AND** the JSON body includes `dsql` with `ok` set to true and `result` set to `1`

#### Scenario: DSQL fails while SSM succeeds
- **WHEN** a client sends an HTTP GET request to `/api/`, the SSM lookup succeeds, and the DSQL probe fails
- **THEN** the response status is 200
- **AND** `cdk_bootstrap_version` still carries the parameter's value
- **AND** `dsql` reports `ok` set to false with an `error` identifier

### Requirement: Database failure does not produce an error status
The `/api/` endpoint SHALL return HTTP 200 for every Aurora DSQL failure mode, including missing configuration, token generation failure, connection failure, and query failure. A database failure SHALL NOT prevent the endpoint from returning the SSM result, and SHALL NOT prevent the static page from being served.

#### Scenario: DSQL is not configured
- **WHEN** `DSQL_CLUSTER_ENDPOINT` or `DSQL_CLUSTER_USER` is absent from the environment and `/api/` is called
- **THEN** the response status is 200
- **AND** `dsql` reports `ok` set to false with the error identifier `not_configured`

#### Scenario: Application starts without DSQL configuration
- **WHEN** the container starts with no DSQL environment variables set
- **THEN** the application starts successfully
- **AND** continues to serve both `/` and `/api/`

#### Scenario: Cluster rejects the credentials
- **WHEN** the cluster refuses the connection because the caller lacks `dsql:DbConnect` on it
- **THEN** the response status is 200
- **AND** `dsql` reports `ok` set to false with the error identifier `connection_failed`

### Requirement: Failure detail is logged, not returned
The system SHALL log the underlying exception detail for every Aurora DSQL failure. The `/api/` response body SHALL carry only a short, stable error identifier and SHALL NOT include raw driver error text, connection strings, host names, user names, or authentication tokens.

The defined identifiers are `not_configured`, `auth_token_failed`, `connection_failed`, and `query_failed`.

#### Scenario: A connection failure occurs
- **WHEN** the DSQL probe fails because the connection could not be established
- **THEN** the underlying exception detail is written to the application log
- **AND** the response body's `dsql.error` field contains only the identifier `connection_failed`

#### Scenario: No token appears in the response
- **WHEN** any DSQL failure is reported through `/api/`
- **THEN** the response body contains no authentication token and no connection string

### Requirement: Status page shows the DSQL result
The static page SHALL display the outcome of the Aurora DSQL connectivity check alongside the CDK bootstrap version, using the data returned by `/api/`.

#### Scenario: Page loads with a successful check
- **WHEN** a client loads `/` and `/api/` reports `dsql.ok` as true
- **THEN** the page shows the DSQL check as successful

#### Scenario: Page loads with a failed check
- **WHEN** a client loads `/` and `/api/` reports `dsql.ok` as false
- **THEN** the page shows the DSQL check as failed together with the returned error identifier
