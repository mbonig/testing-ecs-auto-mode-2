## Context

`app.py` is a single-process Flask app serving a static `index.html` at `/` and a JSON endpoint at `/api/`. Today `/api/` does one thing: `boto3` SSM `GetParameter` for `/cdk-bootstrap/hnb659fds/version`, with a graceful `unavailable` fallback so a missing parameter never produces a 5xx. The container image is `python:3.12-slim` with `flask` and `boto3`.

We now want the same endpoint to also prove the task can talk to an Aurora DSQL cluster. Aurora DSQL is PostgreSQL wire-compatible but authenticates differently from RDS Postgres:

- There is no static password. The password is a short-lived IAM auth token generated by the caller — `boto3.client("dsql").generate_db_connect_auth_token(endpoint, region)` for a non-admin user, or `generate_db_connect_admin_auth_token(...)` for `admin`. Tokens expire (900s by default), so a token cannot be generated once at import time and reused for the process lifetime.
- Connections are TLS-only and the AWS samples connect with `sslmode=verify-full`.
- The endpoint form is `<cluster-id>.dsql.<region>.on.aws`, port `5432`, database `postgres`.
- DSQL caps individual connection lifetime (roughly one hour — the AWS pooling sample sets `max_lifetime=3300`), so long-lived connections must be recycled.

Connection details arrive as environment variables injected by the runtime; the app does not discover or create the cluster.

One constraint worth recording: the ECS/CDK infrastructure commit (`d7396ac`) is not on `main`, and `infra/` in the working tree holds only `node_modules`. Nothing in this change can rely on editing that stack.

## Goals / Non-Goals

**Goals:**
- `/api/` reports whether a `SELECT 1` against the configured DSQL cluster succeeds.
- Connection configuration is entirely environment-driven, with no cluster identifiers hard-coded.
- A DSQL failure — unreachable, unauthorized, unconfigured, or slow — never turns `/api/` into an error response, mirroring the existing SSM fallback.
- The failure reason is visible enough in the JSON body and container logs to diagnose a misconfiguration without shelling into the task.

**Non-Goals:**
- No connection pooling, no persistent connection, no ORM, no migrations, no schema. `SELECT 1` needs none of it.
- No provisioning of the DSQL cluster, IAM policy, security group, or task-definition environment variables. Those live in infrastructure that is not on this branch.
- No change to the SSM behavior or to the `cdk_bootstrap_version` field.
- No new health-check path. The ECS/ALB health check points at `/api/`, and this endpoint must keep returning 200 for a DB outage precisely so a database problem does not cycle otherwise-healthy tasks.

## Decisions

### Use `boto3` + `psycopg` (v3) directly rather than the AWS DSQL connector

`aurora-dsql-python-connector` (`aurora_dsql_psycopg`) generates and refreshes tokens and configures SSL for you, which is genuinely useful for a pooled, long-running workload. For one `SELECT 1` per request, it is two extra dependencies hiding the only two lines that matter. `boto3` is already in `requirements.txt`, so the marginal cost of the direct approach is a single new dependency, `psycopg[binary]`.

`psycopg[binary]` ships a bundled libpq, so no `libpq-dev`/`postgresql-client` apt layer is needed in the slim image and the Dockerfile stays untouched.

This decision has one dependency consequence that only surfaced during implementation: `boto3` is pinned at `1.34.162`, which predates Aurora DSQL and does not have a `dsql` service client at all (`UnknownServiceError`). The direct approach therefore needs a `boto3` upgrade, not just a new package. That upgrade would have been required by the connector route too, since the connector calls the same boto3 API underneath.

*Alternative considered*: `psycopg2-binary`. Rejected — the AWS DSQL samples lead with psycopg 3, and psycopg 3 exposes `pq.version()` so the code can opt into `sslnegotiation=direct` when the bundled libpq is ≥ 17.

### Generate a fresh auth token on every probe

Tokens expire, so caching one in a module-level variable produces an endpoint that works for fifteen minutes after each deploy and then reports a confusing authentication failure. `generate_db_connect_auth_token` is a local SigV4 signing operation — no network call — so regenerating it per request costs essentially nothing.

*Alternative considered*: cache the token with an expiry check. Rejected as premature for a per-request probe; it adds state and a class of staleness bugs to save microseconds.

### Open and close a connection per probe

The probe should answer "can this task connect right now?" A pooled or cached connection answers "could it connect at some point in the past," which is the question that lets a broken cluster look healthy. Per-probe connections also sidestep DSQL's connection-lifetime cap entirely.

*Trade-off*: a TLS handshake plus auth per call, roughly 100–300ms. Acceptable for a status endpoint; it would not be acceptable for a hot data path, and this decision should be revisited the moment real queries are added.

### Pick the token method from the configured user name

The AWS samples branch on `admin`: `generate_db_connect_admin_auth_token` for the `admin` user, `generate_db_connect_auth_token` otherwise. Mirroring that keeps the app working whether it is pointed at a cluster's admin user during early testing or at a least-privilege role in a real deployment.

### Report failure in-band with HTTP 200

The existing SSM path already establishes this pattern with its `unavailable` sentinel, and `/api/` is the container health-check target. Returning 503 on a DSQL outage would make ECS kill and replace tasks that are perfectly capable of serving the page. Instead the response body carries a `dsql` object with `ok`, `result`, and — on failure — `error`.

The proposed shape, additive to the existing key:

```json
{
  "cdk_bootstrap_version": "28",
  "dsql": { "ok": true, "result": 1 }
}
```

```json
{
  "cdk_bootstrap_version": "28",
  "dsql": { "ok": false, "error": "not_configured" }
}
```

Error values are short, stable, machine-readable tokens (`not_configured`, `connection_failed`, `query_failed`, `auth_token_failed`) rather than raw driver text, so the page can render them and a future check can assert on them. The full exception detail goes to the logger, which is where it belongs — driver errors can echo host names and user names, and this endpoint is internet-facing through the ALB.

### Missing configuration is `not_configured`, not a crash

If `DSQL_CLUSTER_ENDPOINT` or `DSQL_CLUSTER_USER` is absent, the app still starts and still serves both routes; `/api/` just reports `not_configured`. The app predates DSQL and must remain runnable — locally, and in any environment where the variables have not been wired up yet — without a database.

### Bound the probe with an explicit timeout

`connect_timeout` is set (5 seconds). Without it, a security-group misconfiguration produces a hung TCP connect, which turns a fast status endpoint into one that ties up a worker until the OS gives up — the ALB health check would then time out and start replacing healthy tasks, which is exactly the outcome the 200-on-failure decision exists to prevent.

No server-side statement timeout is set. Aurora DSQL enforces its own transaction and statement duration limits and does not accept `statement_timeout` as a client-supplied session parameter, so passing `options=-c statement_timeout=...` risks having the *connection* rejected at startup — trading an unbounded query for a probe that never connects at all. `SELECT 1` on a connection that has already completed its TLS handshake and authentication is not a realistic hang risk, and the connect timeout covers the failure mode that actually occurs (unreachable endpoint).

### TLS via the image's CA bundle

The AWS samples reference a downloaded `./root.pem`. DSQL endpoints present a certificate chaining to a public Amazon root that `python:3.12-slim`'s `ca-certificates` package already trusts, so `sslmode=verify-full` works against the system trust store with no bundled PEM and no Dockerfile change. `DSQL_SSLROOTCERT` is honored as an override for environments that pin a specific bundle.

*Risk noted*: this depends on the base image trusting the Amazon root. Task 4 verifies it explicitly rather than assuming, and the override exists as the escape hatch if it does not hold.

## Risks / Trade-offs

- **Per-request connect adds latency to a health-check path** → Timeouts are explicit and short, so worst case is bounded well under the ALB's threshold. If `/api/` ever becomes latency-sensitive, move the probe behind a short TTL cache rather than to a persistent connection.
- **The ALB health check hits `/api/`, so DSQL work now runs on every health check** → The probe stays cheap and always returns 200. It is still a real behavior change: health-check traffic now opens database connections at the health-check interval, which is worth a look at DSQL connection metrics after rollout.
- **`verify-full` against the system trust store may fail if the base image lacks the Amazon root** → Verified in task 4 against a real cluster; `DSQL_SSLROOTCERT` overrides without a code change.
- **Driver error text can leak host, user, or network detail** → Only mapped sentinel tokens go in the response body; full detail goes to the logger.
- **Missing IAM permission produces a token that signs fine but is rejected at connect time** → Surfaces as `connection_failed` with the underlying error logged; the design doc and task list both call out `dsql:DbConnect` so the cause is easy to find.
- **A cached token would have made this endpoint intermittently wrong** → Avoided by generating per probe; recorded here because the caching instinct is strong and the resulting bug is delayed and confusing.

## Migration Plan

1. Ship the code change. With no DSQL environment variables set, `/api/` reports `not_configured` and everything else behaves exactly as before — the change is inert until configured.
2. Inject `DSQL_CLUSTER_ENDPOINT` and `DSQL_CLUSTER_USER` into the task, and attach `dsql:DbConnect` (or `dsql:DbConnectAdmin`) for the cluster to the task role. Confirm the task's egress reaches the cluster endpoint on TCP 5432.
3. Load `/` and confirm the page shows the DSQL result alongside the bootstrap version.

**Rollback**: remove the environment variables — the endpoint degrades to `not_configured` with no redeploy. A full revert of the code change is also safe, since the `cdk_bootstrap_version` field is untouched throughout.

## Open Questions

- Which database user the deployed task will authenticate as (`admin` versus a least-privilege role linked to the task role). The code handles both, so this does not block implementation, but a real deployment should not use `admin`.
- Whether the eventual infrastructure creates a DSQL cluster or adopts an existing one. Out of scope here, but it determines where the endpoint value comes from.
- Whether `/api/` should stay the ALB health-check target once it depends on a second external service. Keeping it is correct as long as the endpoint always returns 200; if that ever changes, the health check needs its own path.
